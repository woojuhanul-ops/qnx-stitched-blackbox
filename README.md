# Stitched Blackbox — a deterministic audit & replay debugger for QNX

**A developer tool for QNX Neutrino RTOS 8.0 that records system events in an
immutable ledger and answers questions about them deterministically — or
abstains.**

Most debugging aids guess. The Stitched Blackbox never does. Events are written
to a fixed-size ledger with coordinates; questions are answered only from that
ledger, with the evidence cell cited. If a fact is not in the ledger, the tool
answers `ABSTAIN_NO_RECORD`. If it cannot answer inside its measured time
budget, it answers `ABSTAIN_TIMEOUT` instead of answering late. A watchdog
demonstrates the QNX microkernel's process isolation: when a sensor process is
killed, only that process is restarted — the ledger server never stops
answering.

Built for the **QNX Global Hackathon 2026** (Developer Tooling category).

## Why it exists

Flight recorders work because they only record, never interpret. This project
applies the same discipline to embedded debugging on QNX:

- **Deterministic retrieval, not generation.** The retrieval core uses an
  Aho-Corasick automaton for record-name matching and hash indexes for
  location/type/role fields. There is no per-query full scan and no
  probabilistic model anywhere in the answer path — the same question always
  produces the same answer (verified: 8,100 repeated queries, 0 mismatches).
- **Abstention as a feature.** Two explicit abstention paths — no record, and
  time-budget exceeded — make the tool's silence trustworthy.
- **Evidence coordinates.** Every answer cites its ledger cell
  (`[row, column]`), so a human can verify it against the ledger in one look.
- **Static memory discipline.** After initialization there is no dynamic
  allocation anywhere. The ledger is a 256-entry static ring buffer; every
  store is a compile-time-sized static array.

## Architecture (4 target modules + host bridge)

| Module | File | Role |
|---|---|---|
| Ledger server | `ledgerd.c` | Owns the 48-row record table and the event ring. Serves APPEND / QUERY / STATS / EVENTS over native QNX message passing (`MsgReceive`/`MsgReply`), registered as `blackbox/ledger`. |
| Retrieval core + gate | `retriever.c`, `retriever.h` | C11 port of the reference retrieval semantics (question templates T1–T9, longest-name-first, abstain on ties). Emits `ABSTAIN_NO_RECORD` / `ABSTAIN_TIMEOUT`; timing measured with `ClockCycles()`. |
| Watchdog + fault injection | `watchdog.c`, `sensord.c` | Spawns and monitors the ledger server and a mock sensor. On sensor death it logs `FAULT` to the ledger, respawns only the dead process, and logs `RESPAWN` when the new sensor is ready. Recovery time is measured end to end. |
| Target verifier | `verifier.c` | Runs the fixed 81-question acceptance exam on-target over IPC and streams per-question JSON over the serial line (phases: exam → budget derivation & re-run → timeout gate → 100× determinism → fault injection). |
| Host bridge | `tools/bridge.py`, `bridge/` | Renders the streamed results in the Stitched Ledger UI (same stylesheet and evidence highlighting), so answers light up their evidence cell. |

Shared protocol and data types: `blackbox.h`. The record table and the exam
are compiled in from `ledger_data.h` / `exam_data.h`, which are generated by
`tools/gen_data.py` from the synthetic 48-row laboratory ledger of the
companion [Stitched Ledger](https://github.com/woojuhanul-ops/stitched-ledger)
project. All records are synthetic; there is no personal data in this
repository.

## Measured results (QNX 8.0 on QEMU 10.2, x86_64)

The acceptance exam is the same 81 questions used to qualify the reference
core on the host (66 retrieval questions, 15 trap questions with no record).
Verdicts were produced twice: by the on-target verifier, and independently by
`tools/check_target.py`, a host checker that shares no code with the verifier
and re-derives every verdict from the original exam definition. The two
verdict sets agreed on every question, in both runs. Full machine-readable
results are in [`evidence/`](evidence/).

| Item | Run 1 | Run 2 |
|---|---|---|
| Retrieval correct | **66/66** | **66/66** |
| Trap abstention (`ABSTAIN_NO_RECORD`) | **15/15** | **15/15** |
| Evidence coordinates correct | **66/66** | **66/66** |
| Server retrieval time — median / mean | 0.037 ms / 0.091 ms | — / 0.101 ms |
| Server retrieval time — p95 / max | 0.374 ms / 0.875 ms | — / 1.564 ms |
| IPC round trip — mean | 0.226 ms | 0.236 ms |
| Time budget (derived, see below) | 17.50 ms | 31.28 ms |
| Budget re-run | identical 81/81, 0 timeouts | identical 81/81, 0 timeouts |
| Timeout gate (1-cycle budget) | `ABSTAIN_TIMEOUT` 3/3 | `ABSTAIN_TIMEOUT` 3/3 |
| Determinism (81 questions × 100) | 8,100 queries, **0 mismatches** | 8,100 queries, **0 mismatches** |
| Fault injection: death detection | 15.80 ms | 15.53 ms |
| Fault injection: full recovery | 28.61 ms | 27.20 ms |
| Ledger server during recovery | pid unchanged, kept answering | pid unchanged, kept answering |

**Honesty notes on the numbers.** All timings are measured *under QEMU
emulation* and are not bare-metal figures. The maximum retrieval time is
dominated by first-question warm-up and emulation jitter (0.875 ms vs
1.564 ms across runs), so the median is the stable representative. The time
budget is not a fixed constant: it is derived per run as **20 × the slowest
measured retrieval**, which is why it differs between runs. Raw serial logs
are not committed; re-running the verifier reproduces them, and the parsed,
independently checked results are committed under `evidence/`.

## Build and run

Prerequisites: QNX SDP 8.0 (host tools `qcc`, `mkifs`), QEMU
(`qemu-system-x86_64`), Python 3 for the host tools.

```bat
:: Windows host, from the repository root — see build.bat
call <SDP>\qnxsdp-env.bat
qcc -Vgcc_ntox86_64 -Wall -O2 -o ledgerd  ledgerd.c retriever.c
qcc -Vgcc_ntox86_64 -Wall -O2 -o sensord  sensord.c
qcc -Vgcc_ntox86_64 -Wall -O2 -o watchdog watchdog.c
qcc -Vgcc_ntox86_64 -Wall -O2 -o verifier verifier.c
mkifs blackbox.build blackbox.ifs
```

`build.bat` and `blackbox.build` are committed exactly as used for the
measured runs; two paths in them reflect the original build machine and must
be adapted on a fresh machine: the SDP location (`D:\QNX\sdp8`) and the
directory holding the built binaries (`D:\Chronica\qnx\blackbox`).

Run under QEMU (see `tools/run_qemu.ps1` for the exact invocation used):

```
qemu-system-x86_64 -cpu max -smp 1 -m 256 -kernel blackbox.ifs \
  -display none -serial file:serial.log -monitor none -no-reboot
```

The verifier runs the full exam automatically at boot and streams JSON
verdicts to the serial log. To check a run independently:

```
python3 tools/check_target.py serial.log   # writes results_target.json
python3 tools/bridge.py                    # renders bridge/index.html
```

A host-side sanity build of the retrieval core (plain gcc, no QNX) lives in
`hosttest/host_main.c`.

## How it was made

Concept and specifications by Dukha Kim (Nexus Group). The deterministic
retrieval core was first built and measured as the browser-based
[Stitched Ledger](https://github.com/woojuhanul-ops/stitched-ledger)
(Kiroween 2026), then re-implemented in C11 for QNX under a factory-line
process with separated maker and checker seats: the core had to pass the
81-question exam on the host before it was allowed onto the target, and every
target verdict was re-derived by an independent checker. Implementation was
carried out with AI assistance (Claude) under human direction; all figures in
this README are measured values from the recorded runs, not estimates.
